Sketchback User Manual

Introduction

Sketchback backs up a Sketchfab account: owned models, collection membership, followers, following, and (for other users you choose to import) their public profile and downloadable models. It stores everything in a local SQLite database plus a plain folder tree of the downloaded files, so the backup stays readable and usable without Sketchback itself.

CLI vs GUI

This manual covers sketchback-cli, the command-line tool -- the non-interactive way to run a backup, script it, or drive it from a cron job or another machine over SSH. Sketchback also ships a desktop GUI (sketchback, built on egui) with the same database and folder layout, a model browser, thumbnails, and a settings UI for the same options this manual documents as flags. A GUI manual is a separate future pass; every concept here (the database, the folder layout, the API token, P2P sync) applies to both, since they are two frontends over the same sketchback-core/sketchback-db/sketchback-app backend.

Where things live

  • Database: <download folder>/models.db -- a SQLite file the CLI creates on first run. Every model, user, and collection row lives here; it is the source of truth for what has been scraped and what has been downloaded.
  • Download folder: where files land. Resolved in this order: the --folder flag, then the GUI's persisted setting (download_folder in settings.toml), then a per-OS default (~/Downloads/Sketchback or similar, via the dirs crate).
  • Settings file: <OS config dir>/sketchback/settings.toml -- e.g. ~/Library/Application Support/sketchback/settings.toml on macOS, ~/.config/sketchback/settings.toml on Linux, %APPDATA%\sketchback\settings.toml on Windows. Holds the saved API token, download folder, rate limit, and P2P sync state, shared between the CLI and the GUI.

See Quick Start to get a token and run the first backup, CLI Reference for every flag, and Workflows for how the flags combine into complete tasks.

Quick Start

1. Get an API token

Sketchback authenticates as you, using a Sketchfab API token (not your password). Generate one at sketchfab.com/settings/password.

2. Provide the token

Any one of these works; the CLI checks them in this order and uses the first it finds:

  1. --api-token <TOKEN> on the command line.
  2. The SKETCHFAB_API_TOKEN environment variable (clap reads it automatically -- equivalent to --api-token, just not typed on every invocation).
  3. A token already saved to settings.toml by the GUI's Settings tab.

If none of these resolve, any command that needs the API fails immediately with an error naming all three options.

3. Run a backup

Download everything for a single Sketchfab collection URL:

sketchback --url https://sketchfab.com/YOUR_USERNAME/collections/YOUR_COLLECTION --api-token YOUR_TOKEN

Or back up a single model:

sketchback --url https://sketchfab.com/3d-models/some-model-slug-0123456789abcdef0123456789abcdef --api-token YOUR_TOKEN

For a full account backup (your own profile, every collection and its members, your followers/following, and every pending download) in one pass, see --auto in Workflows.

4. Resulting folder layout

The download folder ends up looking like this (see crates/sketchback-core/src/storage.rs for the authoritative layout):

<download folder>/
+-- models.db
+-- u/<hash[0:2]>/<hash[2:4]>/<username>/
    +-- avatar.jpg
    +-- c/<collection_uid>.jpg
    +-- m/<uid[0:2]>/<model_uid>/
        +-- source.zip
        +-- model.glb  (or .gltf, .fbx, .obj, ... -- whichever format Sketchfab served)
        +-- thumb.jpg

Each user's files live under a two-level hash shard of their username (u/<h[0:2]>/<h[2:4]>/<username>/), so one very prolific author never dumps thousands of entries into a single directory. Each of that user's models is further sharded by the first two characters of its Sketchfab UID (m/<uid[0:2]>/<uid>/). Nothing about this layout needs the database to resolve -- the same (username, uid) pair always computes the same path, which is what lets --migrate-layout (see Workflows) move old downloads onto it deterministically.

models.db sits at the download folder's root, not inside any user's shard -- it is shared state for the whole folder, independent of any one user or model.

CLI Reference

sketchback-cli is a single clap command with no subcommands -- every mode is selected by which flags are present. Flags are grouped below by what they do; Workflows walks through the full commands each group is meant to be combined into.

Auth and folder

--api-token <TOKEN> (env SKETCHFAB_API_TOKEN)

Sketchfab API token. clap's env = "SKETCHFAB_API_TOKEN" means the flag and the environment variable are interchangeable -- whichever is set wins, flag over env. See Quick Start for the full resolution chain, which also falls back to a token saved by the GUI.

sketchback --api-token abcdef0123456789 --url <url>

-f, --folder <PATH>

Download folder. When omitted, the persisted GUI setting (settings.download_folder) is used, falling back to a per-OS default. Passing this flag explicitly (vs. leaving it unset) is also how the P2P sync commands distinguish "use this folder" from "use whatever settings.toml already has."

sketchback --folder /Volumes/2tb/sketchback-library --url <url>

-r, --rate-limit <SECONDS> (default 45)

Seconds to sleep between each downloaded model (not between API calls -- see --api-delay-ms below for that). Applies to --auto, --download-only, and any --url download.

Scrape and download

-u, --url <URL>

Collection URL or single-model URL to scrape. A URL containing /3d-models/ is treated as one model (its UID is parsed from the URL's trailing hex segment); anything else is treated as a collection and every model in it is scraped. Downloads immediately afterward unless --scrape-only is also passed. See single URL vs collection URL in Workflows.

--scrape-only

With --url pointing at a collection: write the scraped model list (and, if the URL resolves to a real collection UID, its cached_list membership rows) to the database, but do not download anything. Re-running the same --url later without this flag downloads whatever is still pending.

--limit <N> (default 0 = unlimited)

Cap the number of models downloaded in one run. Applies to --url, --download-only, and --auto's final download stage.

--download-only

Download every pending model already in the database, without re-scraping anything first. Use after a --scrape-only run, or any time you just want to resume unfinished downloads.

--retry

Modifies --download-only: instead of every pending model, only download retry candidates -- pending models that either have never been attempted, or failed with a transient error. Models already classified permanently non-downloadable (fab_only, not_found -- see --classify-attempts below) are skipped. The run prints how many were skipped this way.

sketchback --download-only --retry --api-token <TOKEN>

--organize

Move any files sitting in a legacy private/ staging area into their correct location per the database's recorded path, using only local file info -- no network calls.

--import-users <user1,user2,...>

Fetch each comma-separated username's public profile plus every model of theirs the API reports as downloadable, upsert them into the database, and save their avatar. Does not download the models themselves -- follow with --download-only for that.

sketchback --import-users alice,bob --api-token <TOKEN>

Fetch and graph maintenance

These call the Sketchfab API and are paced through the same global rate limiter (--api-delay-ms, with automatic HTTP 429 backoff) -- see Troubleshooting for how the backoff behaves.

--api-delay-ms <MS> (default 1100)

Minimum delay between Sketchfab API calls (not downloads -- see --rate-limit above for that). 1100 ms is about 55 calls/minute, safely under Sketchfab's documented ~60/minute quota. On an HTTP 429 response the effective floor doubles automatically (capped at 5 minutes) and decays back down after 30 consecutive successes -- this flag sets the floor, not a hard ceiling.

--fetch-collections

Fetch the member list of every collection already in the database and populate cached_list (membership rows) for each. Run once after a profile sync has populated the collections table, so collection membership is available offline afterward.

--fetch-user-profiles

Fetch the full profile (display name, bio, counts, avatar) for every user row in the database whose profile is incomplete -- e.g. a "skeleton" user row created only because they appeared as a follower/following/collection member, with no profile fetch of their own yet. Idempotent: users with a complete profile already are skipped.

--fetch-user-graph --user <username>

Fetch collections, followers, and following for an arbitrary user (not necessarily the authenticated account). Requires --user; without it the command errors immediately.

sketchback --fetch-user-graph --user someartist --api-token <TOKEN>

--refresh-self-graph

Wipe the followers and following tables entirely, then re-fetch them for the authenticated user (read from account.uid, populated by a prior --auto run or GUI use). Destructive: see Troubleshooting -- this is a full wipe-and-refetch, not an incremental update, and exists specifically to undo pollution left behind by running --fetch-user-graph for a non-self user (those tables are single-owner: the authenticated account's graph only).

--force-refresh

Modifies --auto: normally, --auto skips a collection's member fetch when the locally cached row count already matches the collection's upstream modelCount, to save API calls. This flag forces every collection to be re-fetched regardless.

--auto

Full self sync in one command: authenticated profile, every owned collection and its members, followers, following, fill in any skeleton user profiles, then download every pending model. See the --auto dispatch order in Workflows for the exact stage sequence -- it always runs in the same order and cannot be reordered from the command line.

sketchback --auto --api-token <TOKEN> --rate-limit 60

Database fixups

Offline, no API calls (aside from --fix-db opening the database, which also triggers a one-time typed-column backfill on users as a side effect of DbHandle::spawn/Database::new).

--migrate-layout

Recompute every downloaded model's folder location from sketchback-core::storage's hash-sharded layout (see Quick Start) and rename its directory into place if it isn't there already, rewriting download_path in the database to match. Idempotent -- safe to re-run; already-correct models are left alone.

This renames real directories on disk. It is not reversible by the tool itself -- see Troubleshooting.

--classify-attempts

Backfill availability_status from stored error text, for models that failed to download and were never classified. A last_error containing "not downloadable" or an HTTP 400 is marked fab_only; an HTTP 404 is marked not_found. Models with a transient error (network timeout, HTTP 5xx) are left NULL so they remain eligible for --retry. Idempotent -- only touches rows where availability_status is still unset.

--repair

Reset the downloaded flag for any model whose recorded file is missing or fails validation, so it re-enters the pending pool.

--fix-db

Runs --classify-attempts, then --migrate-layout, then --repair, then --organize, back-to-back, with no Sketchfab API calls. The one-command way to clean up a database and folder after interrupted runs or manual file moves -- see the --fix-db chain in Workflows.

sketchback --fix-db

P2P sync

Dispatched before any of the above -- if any P2P flag is present, none of the Sketchfab-API setup runs. Full detail, including the write-secret warning on the pairing ticket, is in P2P Sync.

--sync-init

Initialize this machine as the first peer: creates the sync document, exports the local database and files, and prints a pairing ticket.

--sync-join <TICKET>

Join an existing peer using a ticket printed by --sync-init on another machine.

--sync

One-shot reconcile: export local changes, pull remote ones, then exit. Requires a prior --sync-init or --sync-join on this machine.

--sync-daemon

Run continuous bidirectional sync until Ctrl-C. Requires a prior --sync-init or --sync-join.

Workflows

This chapter walks through each distinct thing Sketchback can do end to end. CLI Reference documents each flag individually; this chapter is about how they combine.

Single model vs collection URL

--url behaves differently depending on the URL shape (crates/sketchback-cli/src/url_command.rs):

  • https://sketchfab.com/3d-models/<slug>-<uid> -- a single model. The UID is parsed off the end of the URL (the trailing hex segment). Its metadata is fetched to get the name and author, upserted into the database, and it is downloaded immediately (unless --scrape-only).
  • Anything else -- treated as a collection URL. The whole collection is scraped via the API (or, if --scrape-only was used on a prior run and the collection is already cached, read straight from the database instead of hitting the network again), every model upserted, and -- if the URL resolved to a real collection UID -- cached_list membership rows written too, so a later offline pass (or another tool reading the same database) can see the membership without re-scraping.

Both paths print a numbered [downloaded]/[pending] status list before downloading, and both route the actual download through the same shared orchestrator::download_pending loop as every other download path in this manual -- so DB updates, classification, and logging are identical regardless of how a model was found.

sketchback --url https://sketchfab.com/USERNAME/collections/COLLECTION --api-token <TOKEN>
sketchback --url https://sketchfab.com/3d-models/some-slug-0123456789abcdef0123456789abcdef --api-token <TOKEN>

--auto: full self sync

--auto runs five stages, always in this fixed order, and cannot be reordered or partially selected from the command line:

  1. Self identity -- resolve the authenticated account's own uid and username, fetching them if not already known. Every later stage needs this (see the account.uid precondition in Troubleshooting).
  2. Profile + my_collections + members -- fetch the authenticated user's profile, every collection they own, and every model in each of those collections (skipping a collection whose cached row count already matches its upstream modelCount, unless --force-refresh is passed).
  3. Followers + following -- refresh the authenticated user's social graph (the same wipe-and-refetch --refresh-self-graph does on its own).
  4. Skeleton profiles -- fill in full profile data for any user row that only exists as a stub (someone who showed up as a follower, a following, or a collection member, but was never fetched directly).
  5. Download pending -- download every retry-eligible pending model (same candidate set --download-only --retry uses), respecting --rate-limit between files.

A stage that partially fails (a single API call erroring out) logs it and moves on to the next stage rather than aborting the whole run -- --auto is meant to be safe to re-run after a partial failure; whatever didn't complete just gets picked up again next time.

sketchback --auto --api-token <TOKEN>

--download-only and --retry

--download-only downloads whatever is already pending in the database without scraping anything first -- the natural follow-up to a --scrape-only run, or to resume after --auto/--url was interrupted. Add --retry to skip models already classified permanently non-downloadable (see --classify-attempts below) instead of retrying them every time.

sketchback --download-only --retry --limit 50 --api-token <TOKEN>

--organize and --repair

Two independent offline (no-API) passes:

  • --organize moves files sitting in a legacy private/ staging area into their correct location per the database's recorded path.
  • --repair resets the downloaded flag for any model whose file is missing or fails validation on disk, so it becomes pending again.

--fix-db: offline cleanup chain

--fix-db chains four offline (no-API) passes in one fixed order: classify-attempts -> migrate-layout -> repair -> organize. This order matters -- classification needs to happen before repair resets anything, and migrate-layout needs to run before organize looks for files in their expected location. Each pass prints its own progress; nothing here touches the network. The one-command way to clean up a database and folder after interrupted runs or manual file moves.

sketchback --fix-db

--import-users

Fetches profile + downloadable-models metadata for each comma-separated username and upserts it into the database, saving each user's avatar along the way. It does not download the models themselves -- follow it with --download-only (or --auto, which does not include imported users' models in its own pending set unless they were already scraped).

sketchback --import-users alice,bob,carol --api-token <TOKEN>
sketchback --download-only --api-token <TOKEN>

--migrate-layout

Recomputes every downloaded model's folder from sketchback-core::storage (see Quick Start) and renames its directory into place, rewriting download_path to match. Run this after any manual reorganization of the download folder, or after upgrading from an older Sketchback version that used a different layout. Idempotent: a model already in the right place is left alone and counted separately from ones actually moved.

This renames real directories on disk and cannot be undone by the tool. See Troubleshooting: destructive operations before running it on a folder you have not backed up.

sketchback --migrate-layout

--classify-attempts

Backfills availability_status for models that failed to download and were never classified, by pattern-matching their stored error text: "not downloadable" or HTTP 400 becomes fab_only; HTTP 404 becomes not_found. Both are permanent states --retry then skips. A transient error (timeout, HTTP 5xx) is left unclassified so the model stays retryable. Idempotent -- only rows with no availability_status yet are touched.

sketchback --classify-attempts

The --fetch-* / --refresh-self-graph family

These fill in graph data outside the fixed --auto sequence, one gap at a time:

  • --fetch-collections populates cached_list membership for every collection already in the database -- run once after a profile sync has populated the collections table itself.
  • --fetch-user-profiles fills in full profile data for every incomplete ("skeleton") user row -- the same step --auto runs as its stage 4, available on its own.
  • --fetch-user-graph --user <username> pulls collections, followers, and following for an arbitrary user, not just the authenticated account. Requires --user.
  • --refresh-self-graph wipes the followers and following tables and re-fetches them for the authenticated account (read from account.uid). Exists specifically to undo pollution left behind by running --fetch-user-graph against a non-self user, since those two tables are single-owner (the authenticated account's graph only) -- running --fetch-user-graph --user someone-else does not touch them, but mixing up which command to run for which purpose is an easy mistake. See Troubleshooting: destructive operations.

All four are paced through --api-delay-ms with the same HTTP 429 backoff as every other API call -- see Troubleshooting.

sketchback --fetch-user-graph --user someartist --api-token <TOKEN>
sketchback --refresh-self-graph --api-token <TOKEN>

P2P Sync

Sketchback can replicate its database and downloaded files directly between your own machines, peer to peer, over one iroh node -- no server, no account, no third party in the loop. Database rows travel as iroh-docs entries (per-key last-writer-wins CRDT); files travel as iroh-blobs, content-addressed by BLAKE3 hash.

P2P sync commands are dispatched before any of the Sketchfab API setup the other commands need (crates/sketchback-cli/src/main.rs) -- if any of the four flags below is present, nothing else in this manual's CLI Reference runs for that invocation.

The pairing ticket is a write secret

The very first thing to know: the ticket --sync-init prints is not a read-only invite link -- holding it grants full read/write access to the synced database and files. There is deliberately no separate allowlist of which machines may connect (a second check would block initial pairing, since the first machine cannot know the second machine's identity before it connects) -- the ticket itself is the entire authorization boundary. Treat it like a password: share it over a channel you trust, do not paste it into a public chat or issue tracker, and do not log it anywhere.

── pairing ticket (write secret -- share securely) ──
<long ticket string>

--sync-init: first machine

Run once, on whichever machine already has (or will have) the database you want to treat as the starting point. Creates the sync document, exports the current local database and files into it, and prints the pairing ticket.

sketchback --sync-init

--sync-join <TICKET>: second (and further) machines

Run on every other machine, pasting in the ticket --sync-init printed. Imports the ticket and projects the remote state onto this machine's local database and download folder.

sketchback --sync-join <TICKET>

--sync: one-shot reconcile

Exports this machine's local changes, pulls in whatever changed on other peers, then exits. Requires a prior --sync-init or --sync-join on this machine. Good for a manual "sync now" from a script or cron job.

sketchback --sync

--sync-daemon: continuous sync

Same reconcile as --sync, but keeps running (bidirectional, continuous) until Ctrl-C. Requires a prior --sync-init or --sync-join.

sketchback --sync-daemon

What does and does not sync

  • Database rows sync as a last-writer-wins CRDT, per row. Machine-local columns -- download_path and anything else that is really "where does this file live on THIS disk" -- are never projected from a peer; they are recomputed locally from (root, author, uid) on each machine instead, and downloaded is derived from whether the file is actually present after projection.
  • Files sync content-addressed by BLAKE3 hash, independent of the database rows that reference them.
  • This machine's node identity (an iroh SecretKey) is generated once and stored at <sync_dir>/node.secret, owner-only permissions. It is deliberately kept out of the readable settings.toml. It is stable forever once created -- regenerating it orphans every existing pairing, so back that file up along with the rest of your sync state if you care about not having to re-pair.

--folder overrides which download folder (and therefore which models.db) a sync command operates on, the same as every other command in this manual -- useful for syncing a folder other than the persisted GUI setting.

sketchback --sync-daemon --folder /Volumes/2tb/sketchback-library

Troubleshooting

"API token required"

Every command that talks to the Sketchfab API resolves a token through a fixed chain (require_api_token, crates/sketchback-cli/src/args.rs), in this order:

  1. --api-token <TOKEN> on the command line.
  2. The SKETCHFAB_API_TOKEN environment variable -- clap's env = "SKETCHFAB_API_TOKEN" folds this into the same field as --api-token, so either one satisfies step 1/2 together; whichever is actually set is what gets used.
  3. Settings::load().api_token -- a token already saved to settings.toml by the GUI's Settings tab.

If none of the three resolve, the command fails immediately with an error listing all three options and a link to generate a token. There is no fourth fallback and no interactive prompt -- a script relying on this command should set one of the first two explicitly rather than depending on a machine's saved GUI settings existing.

Rate limiting: --rate-limit vs --api-delay-ms, and HTTP 429

These two flags gate two different things and are easy to confuse:

  • --api-delay-ms (default 1100) paces API calls -- metadata fetches, pagination, graph fetches. 1100 ms is about 55 calls/minute, under Sketchfab's documented ~60/minute quota.
  • --rate-limit (default 45, seconds) paces downloads -- the sleep between one finished model and the start of the next one.

Both exist because a sync run makes many small API calls and relatively few large downloads; conflating the two into one setting would either throttle API calls far more than needed or not throttle downloads enough.

On an HTTP 429 response, the API-call floor (--api-delay-ms's effective value) doubles automatically, capped at 5 minutes, and the same request retries up to 3 times honoring the server's Retry-After header when present. After 30 consecutive successful calls the floor decays back toward the configured value. This is process-wide and shared across every Sketchfab API call in the run (including ones from --fetch-* flags running concurrently with other work) -- so a 429 anywhere raises the floor for everything, not just the call that triggered it. Full detail: docs/rate-limit.md in the repository.

If a run is hitting 429s persistently, raising --api-delay-ms above the default before starting is more effective than relying on the backoff to find a stable floor on its own -- the backoff reacts after the fact.

"account.uid not set"

Any graph command that operates on the authenticated account itself (--refresh-self-graph, and --auto's stage 3) needs account.uid already populated in the database. It is written the first time the account's own profile has been fetched -- by a prior --auto run, or by opening the GUI once (which fetches it on startup). Running one of these commands before that has ever happened fails with:

account.uid not set — run sketchback GUI once or `sketchback-cli --auto`

The fix is exactly what the message says: run sketchback --auto once (which resolves account.uid in its first stage, before any later stage needs it -- see Workflows), or open the GUI once, then retry.

Destructive operations

Two commands change on-disk state in ways this tool cannot undo for you. Both are otherwise safe and idempotent to re-run -- the risk is entirely in the first run against data you have not backed up.

--migrate-layout renames real directories

--migrate-layout (and the --fix-db chain, which includes it) moves every downloaded model's directory to match the current hash-sharded layout (see Quick Start), and rewrites download_path in the database to match. This is a real filesystem rename, not a copy -- there is no "undo" command. If a rename fails partway (permissions, a file locked by another process, disk full), the directory may end up in neither the old nor the fully-correct new location for that one model. Back up the download folder (or at least models.db) before running this against a large, valuable library for the first time.

--refresh-self-graph wipes before it re-fetches

--refresh-self-graph (and --auto's stage 3) deletes every row in the followers and following tables before re-fetching them from the API. Those two tables are single-owner -- they only ever hold the authenticated account's own graph -- which is exactly why the wipe is safe under normal use. But if the re-fetch fails partway (network error, API outage, token revoked mid-run), the tables are left empty rather than rolled back to their pre-wipe state, until the command is re-run successfully. This does not touch any other table -- collections, models, and non-self user profiles are unaffected.
